## Status and authority

This additive milestone is authorized by `author-01` on 2026-09-02. It governs the product
workflow added after the frozen M3 evaluation and immutable M4 presentation snapshot. If this

## Immutable boundary

M4.1 consumes but never regenerates, modifies, reinterprets, or replaces:

- the 30-case benchmark, split, families, labels, or digest;
- completed Phase 1 or Phase 2 live artifacts;
- frozen prompts, schemas, rules, or configurations used by Phase 2;
- the M4 presentation snapshot and presentation-correction ledger;
- validation or live paper tables and existing performance claims.

A separate M4.1 protected-artifact manifest records the pre-implementation SHA-256 values and the
verification command fails if any protected byte changes. Product execution profiles, prompt
versions, snapshots, screenshots, and results are additive and separately versioned.

The following disclosures remain invariant: FDA/CDER-only; eCTD v3.2.2 source and v4.0 target;
prospective forward-compatibility research scenario; current FDA operational availability
`not_operational`; `expert_validated: false`; author-adjudicated rules are controlled research
operationalizations; no FDA acceptance, compliance, submission-readiness, or regulatory-advice
claim; only public, synthetic, or deliberately de-identified uploads.

## Capability boundary

The UI and documentation use this exact statement:

> RegBridge securely parses and validates a controlled FDA eCTD v3.2.2 package profile for supported structural, lifecycle, metadata, checksum, and document-evidence predicates. It does not perform complete FDA submission validation.

Profile ID: `fda-ectd-322-regbridge-demo-profile-v1`.

The profile supports one sequence root at the extraction root or below one application/sequence
wrapper. It reports scoped check statuses (`passed`, `warning`, `unsupported`, `failed`) instead
of a generic eCTD-valid boolean. It recognizes an allowlisted eCTD DOCTYPE without network or
filesystem resolution and records `dtd_validation_performed: false`; complete DTD and FDA
validation remain out of scope.

The profile verifies legacy MD5 values only for format compatibility, using a narrowly scoped
non-security calculation, and retains independent SHA-256 provenance. It distinguishes backbone,
regional, dossier-document, study-tagging, support, and unsupported members. Only supported
dossier PDFs become analysis candidates. Lifecycle records preserve `modified-file` references
and explicitly report unresolved prior-sequence history.

## Product architecture

### Upload and inventory

`POST /api/v1/applications/parse` accepts the bounded ZIP and discards raw bytes after parsing.
`GET /api/v1/applications/{inventory_id}` returns a typed inventory by opaque server ID. The local
repository is capacity bounded and TTL based; records do not survive server restart. It rejects
malformed/traversal-like IDs and never logs full PDF text.

### Model profiles

`GET /api/v1/models` exposes safe public metadata only. `gpt-5.5` is the default and becomes
available only with valid server-side Responses configuration; no temperature parameter is sent.
`qwen3.6-local` is visible as `coming_soon`, disabled, and never called. It reserves a capability-
checked chat-completions adapter boundary without asserting Responses or strict-schema support.
Browser requests supply only an allowlisted `model_id`.

Every applicable product result records the profile ID, requested and provider-reported model,
adapter, configuration digest, prompt version, request digest, usage, latency, and bounded status.
Run identity includes the execution profile/configuration digest. Same package, leaf, target, and
configuration have stable identity; changing model/configuration changes identity.

### Dossier analysis

`POST /api/v1/dossier-analyses` and `GET /api/v1/dossier-analyses/{run_id}` implement explicit
`queued`, `running`, `completed`, `partial_failed`, and `failed` states. The selected model and
target context are explicit. Leaf failures never become permissive decisions. Only transport or
provider-API failures receive bounded retry; schema, citation, graph, persistence, or synthesis
failures roll back the affected leaf and are non-retryable.

### Package comparison

`POST /api/v1/comparisons` and `GET /api/v1/comparisons/{comparison_id}` run fixed B0, B1, B2,
and RegBridge systems on the same label-free, package-derived facts. B0 receives all six standards
spans; B1 receives the frozen BM25 top three; B2 is model-free; RegBridge runs the hybrid path.
B0/B1 receive the complete shared six-decision/eleven-action vocabulary and no benchmark IDs,
fixture IDs, labels, expected rules/evidence, adjudication rationales, or RegBridge result.

Arbitrary-upload comparison reports decisions, actions, evidence coverage, disagreement,
failures, latency, usage, and native traces. It never reports accuracy, reference decisions,
unsafe-FNR, review bypass, correctness, a winner, rankings, or superiority.

## User interface

Navigation is `Analyzer | Baselines | Evaluation | Guided cases | About`.

- `/` uploads and analyzes a dossier, displays controlled profile checks, inventory summary,
  decisions, severity, repair/check, findings, evidence, uncertainty, model record, chronological
  trace, and accessible graph/edge table. It contains no baseline or benchmark output.
- `/baselines` uploads or reuses an inventory and compares the four systems without labeled
  metrics. GPT-5.5 is selectable; Qwen is visibly disabled; B2 is `No LLM`.
- `/evaluation` remains the immutable held-out Phase 2 dashboard.
- `/demo/case-a`, `/demo/case-b`, and `/demo/case-c` remain regression/guided routes.
- `/about` receives the previous scope page.

Metadata intent is never inferred silently: the target-context panel shows and requires
confirmation of preservation/normalization intent and manufacturer partitioning when applicable.
Current-operational mode visibly reports forward compatibility unavailable.

## Composite dossier

The deterministic public package is generated under `data/demo-dossiers/m4-1/` with a separate
manifest. ZIP member order/timestamps, XML, PDFs, legacy MD5 values, `index-md5.txt`, and SHA-256
provenance are reproducible. The uploaded package contains no expected result or hidden lookup key.

Signals are derived from uploaded content:

1. Case A heading comes from the `index.xml` hierarchy.
2. Case B `manufacturer="all"` comes from its XML attribute and preservation intent remains a
   visible target-context input.
3. Case C stale applicant wording comes from PDF text and is compared with the applicant parsed
   from `m1/us/us-regional.xml`.

Metamorphic tests move A to `3.2.S.1`, replace B's manufacturer with a stable distinguishing
value, and make C's applicant prose agree with regional metadata. Each must alter the production
finding/result through the same upload, parser, analyzer, graph, and synthesis boundary.

## Verification gates

`scripts/m4-1-verify.ps1` and `make m4-1-verify` run:

- backend lint, strict typecheck, complete unit/integration/security tests, schema/OpenAPI drift;
- frontend lint, typecheck, unit tests, production build, Playwright E2E and axe accessibility;
- deterministic composite generation and hash verification;
- network-free real-ZIP product demonstration;
- two identical fixture/stub runs;
- protected M3/M4 pre/post hash validation.

The E2E journey uploads the generated ZIP through the public endpoint. Completion requires two
full successful verifier runs and a final report of exact commands/counts, routes, package hash,
screenshots, limitations, and approved deviations.
