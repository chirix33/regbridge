# M4.2 — Public-Standards eCTD v3.2.2 Input Compatibility

## Status and authority

This additive milestone is authorized by `author-01` on 2026-09-03. It extends M4.1 input
compatibility without changing the frozen research evaluation or the existing M4.1 package.

Profile ID: `fda-cder-ectd-322-public-standards-profile-v1`  
Profile version: `1.0.0`

The profile is an FDA/CDER-scoped research-prototype input contract. It is not complete FDA
submission validation, a submission-readiness assessment, production conversion, eCTD v4.0
generation, regulatory advice, or a prediction of FDA acceptance.

## Immutable boundary

M4.2 must not change the frozen M3 benchmark, labels, families, prompts, evaluation
configurations, Phase 1 or Phase 2 artifacts, M4 presentation snapshot, paper tables, numerical
claims, author-adjudicated migration rules, migration decisions, or existing M4.1 package bytes.
A separate M4.2 protected-artifact manifest records pre-implementation file/tree SHA-256 values
and the verifier records and compares post-implementation values.

The following remain invariant: FDA/CDER-only scope; `prospective_forward_compatibility`;
current availability `not_operational`; `expert_validated: false`; public, synthetic, or
deliberately de-identified content only; and the explicit Case A mapping limited to
`3.2.S.1.1`, `3.2.S.1.2`, and `3.2.S.1.3` to `3.2.S.1`.

## Supported input profile

The accepted envelope is exactly:

- FDA/CDER;
- ICH eCTD v3.2.2 backbone specification;
- ICH eCTD DTD v3.2;
- FDA Module 1 specification v2.6;
- US regional DTD v3.3;
- exactly one selected sequence at archive root, `0000/`, or under one application wrapper as
  `application/0000/`;
- bounded PDFs as the only documents eligible for semantic analysis.

The parser may recognize other standard v3.2.2 structural headings for inventory purposes, but
that does not add v4 migration mappings. It remains ambiguous and unsupported to infer a target
mapping merely from a parsed heading.

## Additive pinned input-profile registry

M4.2 uses `data/input-profiles/fda-cder-ectd-322-public-standards-v1/manifest.yaml`. This registry
is separate from the frozen regulatory evidence snapshot. Each record contains a stable ID,
official URL, retrieval timestamp, version, immutable local path, SHA-256 digest, authority,
intended parser use, and whether it is executable validation material.

The registry covers:

1. ICH/FDA eCTD Backbone File Specification for Modules 2 through 5 v3.2.2;
2. ICH eCTD DTD v3.2 and every local DTD dependency needed by it;
3. FDA eCTD Backbone Files Specification for Module 1 v2.6;
4. US regional DTD v3.3 and every local DTD dependency needed by it;
5. selected applicable FDA eCTD validation criteria used only to define parser warnings or
   supported-profile failures.

No profile asset is retrieved or refreshed at runtime. Replacing an asset requires a new
profile version and manifest entry.

## Safe XML and DTD contract

Approved DOCTYPE declarations are recognized while network retrieval, untrusted filesystem
resolution, entity expansion, archive-supplied DTD execution, and every external resource
outside the exact local catalog are disabled.

The catalog maps each approved official absolute HTTP/HTTPS system identifier and approved
standard relative identifier to one pinned local DTD file. Parsing uses a locked-down XML parser
and a custom resolver. The resolver never falls back to URL, current-directory, archive, or
ambient filesystem resolution.

The parser rejects:

- an internal subset or entity declaration;
- an unknown public/system identifier, including an unknown absolute URL;
- a DOCTYPE/root/namespace combination outside the profile;
- a stylesheet, schema, entity, or DTD lookup outside the exact catalog;
- a DTD found in the uploaded archive as a source of validation code.

The ICH backbone must use root `ectd` in namespace `http://www.ich.org/ectd`. The FDA regional
backbone must use root `fda-regional` in namespace `http://www.ich.org/fda` and US regional DTD
v3.3. A missing `index.xml` `dtd-version` attribute is allowed when the approved
DOCTYPE/root/namespace identifies the version; the inventory records a warning and the inference
basis. Unsupported or conflicting declared versions fail with a precise profile error.

Independent DTD validation uses the same pinned local files through a separately callable
validator boundary; the RegBridge inventory parser is not the sole conformance oracle.

## Inventory and lifecycle behavior

The package inventory distinguishes `BACKBONE_XML`, `REGIONAL_XML`,
`STUDY_TAGGING_FILE`, `SUPPORT_FILE`, `DOSSIER_DOCUMENT`, and `UNSUPPORTED` members. The required
`index.xml` leaf that references `m1/us/us-regional.xml` is recorded as a backbone relationship
and never analyzed as a PDF.

Authentic descriptive Module 3 elements such as `m3-2-s-1-1-nomenclature`,
`m3-2-s-1-2-structure`, and `m3-2-s-1-3-general-properties` normalize to `3.2.S.1.1`,
`3.2.S.1.2`, and `3.2.S.1.3`; descriptive suffixes are labels, not heading segments.
Substance and manufacturer metadata are inherited from `m3-2-s-drug-substance` using the
standard attribute names. Module 1 company name and applicable application/submission fields are
parsed from their standard locations.

An authentic `modified-file` such as `../0001/index.xml#leaf-id` is a lifecycle reference, not
an archive member path. If the selected upload lacks the referenced history, the document is
retained with `INSUFFICIENT_APPLICATION_HISTORY`. File `href` values continue through the strict
archive-member path validator. Declared MD5 checksums are verified for legacy compatibility;
SHA-256 is recorded separately for research provenance.

## Migration-policy coverage

Every parsed dossier document has exactly one status:

- `EVALUATED_WITH_APPROVED_POLICY` — at least one approved M4 policy condition is applicable;
- `NO_MIGRATION_CHANGE_DETECTED` — an explicitly encoded clean-negative policy condition applies;
- `OUTSIDE_ENCODED_POLICY_COVERAGE` — parsing succeeded but no encoded migration policy covers
  the document;
- `INSUFFICIENT_APPLICATION_HISTORY` — lifecycle interpretation requires absent prior sequences;
- `DOCUMENT_INSPECTION_INCOMPLETE` — bounded PDF inspection failed or stopped at a limit.

Only an explicit clean-negative condition can produce `NO_MIGRATION_CHANGE_DETECTED`.
Structural acceptance alone never yields `REUSE_AS_LEGACY_REFERENCE`. Analyzer and the four
comparison systems consume the same inventory and coverage record. Out-of-coverage and incomplete
documents remain visible and resolve to human review rather than a permissive reuse decision.

## Demonstration package and product behavior

The deterministic package is additive under `data/demo-dossiers/m4-2/`. It contains authentic,
DTD-valid ICH `index.xml`, DTD-valid FDA `m1/us/us-regional.xml`, their required backbone
relationship, correct namespaces and attributes, verified MD5 values, and three synthetic PDFs
that carry the existing Case A, B, and C signals. It contains no expected decision, benchmark or
fixture ID, hidden label, or adjudication rationale. `manufacturer="all"` occurs on the standard
drug-substance ancestor.

Analyzer remains RegBridge-only. Baselines remains the B0/B1/B2/RegBridge comparison over the
same parsed upload. Both expose profile ID/version, detected DTD identities, validation result,
sequence root, warning count, and policy-coverage counts. Unsupported and out-of-coverage
documents are shown without a safe-reuse claim. Arbitrary-upload pages show no benchmark metric,
winner, ranking, or reference label. The demo preset and documentation point to the M4.2 package.

## Verification gates

`scripts/m4-2-verify.ps1` and `make m4-2-verify` must pass twice. The verifier covers:

- independent local-DTD validation of both generated XML backbones;
- the separately generated acceptance ZIP when present, with a reported missing path otherwise;
- official absolute and standard relative identifiers with zero network access;
- version inference, root/namespace/version conflicts, authentic headings and metadata,
  regional relationship classification, lifecycle references, and supported wrappers;
- XXE, internal subsets, hostile archive DTDs, unknown identifiers, path escape, archive bombs,
  and ambiguous roots;
- explicit policy-coverage behavior and shared Analyzer/B0/B1/B2/RegBridge inventory inputs;
- absence of label, fixture, benchmark, and adjudication leakage;
- two-run package, inventory, and result digest reproduction;
- complete backend lint/type/tests/schema checks, frontend lint/type/tests/build/E2E, and unchanged
  protected-artifact hashes.

The final implementation report records exact changed files, profile/package identifiers,
standards digests, package digest, independent validation results, acceptance-package outcome,
warnings, two-run reproducibility digests, test counts, protected-artifact results, remaining
limitations, and a concise paper-impact note. The paper itself is not modified in M4.2.
