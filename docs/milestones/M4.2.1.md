# M4.2.1 — Independent-package DTD adjudication

## Scope

M4.2.1 is a narrowly additive input-adjudication correction to M4.2. It does not change the
FDA/CDER scope, migration policies, author-adjudicated rules, decision precedence, product flow,
frozen benchmark, Phase 1 or Phase 2 outputs, M4 presentation artifacts, numerical claims, or the
accepted M4.2 demonstration package.

The adjudicator examines a bundled `ich-ectd-3-2.dtd` only as untrusted data. It never parses,
executes, or resolves XML through the archive copy. Both backbone XML files are independently
validated against RegBridge's digest-verified, pinned local ICH/FDA DTDs.

## Comparison contract

For an archive-supplied ICH DTD, RegBridge records:

- archive and pinned SHA-256 digests and byte lengths;
- exact raw-byte equality;
- normalized-text equality after strict UTF-8 decoding, removal of one leading BOM, conversion of
  CRLF or CR to LF, and removal of trailing whitespace on each line;
- semantic equality after XML comments, the XML declaration, and blank lines are removed;
- a classification of `byte_identical`, `non_substantive_text_only`, `comment_only`, or
  `substantive`;
- the first aligned semantic differences, with source line numbers and bounded text;
- whether hostile constructs were found and whether the archive copy was ignored.

The hostile-construct check operates on comment-free normalized text and rejects external
`SYSTEM` or `PUBLIC` entity declarations, nested DOCTYPE declarations, conditional DTD sections,
NUL bytes, and non-UTF-8 content. This check is defensive only: the archive DTD remains ignored
even when it is safe.

## Official byte-integrity basis

The pinned FDA *Specifications for eCTD Validation Criteria* v4.6, criterion 1130 (PDF page 9),
states that a required file checksum in the UTIL folder must match the expected checksum and
identifies an altered DTD or stylesheet as the problem. The pinned ICH DTD record also carries
the official MD5 `1d6f631cc6b6357f0f4fe378e5f79a27`. This is the exact official basis for
requiring byte identity in the declared FDA/CDER profile.

The ICH eCTD Specification v3.2.2 additionally states on PDF page 14 that the actual eCTD XML DTD
should not be changed or altered and, in Appendix 2 on PDF page 93, that the DTD version used to
create the submission must be included. These statements support the interpretation but are not
used as a new migration rule.

## Adjudication policy

1. A hostile bundled DTD causes a hard `security_violation` rejection before XML analysis.
2. Otherwise, `index.xml` is independently validated against the pinned ICH DTD and
   `m1/us/us-regional.xml` against the pinned FDA regional DTD.
3. Failure of either XML yields `rejected_nonconforming` with every pinned-DTD validation error
   recorded. A DTD digest difference is not substituted for the actual XML validation result.
4. When both XML files pass and the archive DTD is byte-identical, the package may continue
   through the ordinary M4.2 parser.
5. When both XML files pass and the archive DTD differs:
   - a profile with no exact official byte-identity requirement accepts using the pinned DTD and
     emits `ARCHIVE_DTD_DIFFERS_FROM_PINNED_COPY`, explicitly stating that the archive copy was
     ignored;
   - this FDA/CDER profile retains `rejected_nonconforming` because criterion 1130 supplies the
     exact checksum requirement. The comparison class and first semantic differences remain
     visible so a line-ending-only change is not misreported as a substantive DTD change.
