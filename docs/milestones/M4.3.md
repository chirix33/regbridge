## Product presentation v1.0.0

`frontend/src/api/presentation.ts` projects the recorded decision, overall document repair,
findings, coverage, model-execution status, uncertainty, and approval requirement together.
It never parses rationale or graph labels into structured findings. Unknown combinations keep
the recorded recommendation and technical record with an explicit presentation limitation.

Needs attention is the default; All documents also exposes scoped clean results and documents
not analyzed. Execution failures are service issues with no regulatory decision. Coverage gaps,
missing history, incomplete inspection, human approval, and proposed context/metadata actions
remain distinct, and multiple statuses can coexist. Status counts may overlap. Review items and
unique document paths are counted separately; leaf-specific conditions remain individually
inspectable even when multiple leaves reference one document.

The overview's areas come from structured recorded states, never sample IDs or titles. It uses
Area / What was found / Recommended next step / Affected documents / Status, becoming labeled
cards when the columns no longer fit. Grouping requires exact agreement in recommendation,
repair description, findings, coverage basis, source heading, metadata, inspection qualifications,
approval, confidence, and uncertainty. It is intentionally conservative. A group retains each
document's title, filename, source locator, findings, citations, and overall repair. A finding
does not receive an invented independent repair.

Opening an action focuses its heading and immediately reveals each document's identity and
Current / Recommended / Why / Next step. Proposed lifecycle/context actions require the recorded
review/approval; the interface never claims to have performed edits or a migration. Supporting
evidence and technical reasoning have separate disclosures. The latter contains codes, execution,
trace, graph, accessible text and edge table, and provenance/digests. Closing returns focus to
the originating action button.

`ProductExplanation` v1.0.0 is an additive product-only payload. RegBridge/B2 retain their native
findings, repair description, evidence, uncertainty, and confidence. B0/B1 retain only their
native explanation and actual cited evidence; unavailable fields remain null and disclosed.
They never inherit RegBridge rules/findings/graph. Source titles, versions, links, and digests
are resolved from pinned records only after identity and digest correspondence checks. A missing
metadata match becomes a presentation limitation, not an analysis failure or invented citation.

Case A plus abstention retains the hard context recommendation and mandatory repair with
incomplete inspection and approval visible. Case B/C abstention does not manufacture stale
content findings. Supported semantic concerns retain the quoted evidence and bounded verification
task. B2 explicitly omits semantic inspection; omission is neither abstention nor clearance.

## Setup and configuration contract

Analyzer and Baselines share target-context controls. Analyzer saves the effective context with
the parsed inventory identity. Baselines carries it unchanged for that inventory; missing or
invalid saved context starts with `unspecified` metadata intent, not preservation. Reading a new
ZIP resets to explicit undecided intent. Editable setup and polling recovery remain available;
retrying a status read does not submit another run.

`DossierAnalysisRequest` and `ComparisonRequest` accept `inventory_id`, `target_context`, and
optional `leaf_ids`. Request-level `model_id` overrides are removed and rejected by the existing
`extra="forbid"` boundary. Existing product clients must update. Evaluation contracts are unchanged.

`GET /api/v1/config/product` exposes the read-only active configuration, including availability,
execution mode, evidence transmission, profile ID, and a safe configuration digest. It replaces
browser model selection. The older `/api/v1/models` endpoint is a read-only compatibility catalog.

- `PRODUCT_MODEL_PROFILE=gpt-5.5`: the single validated active product profile.
- `LLM_MODE=fixture`: explicit offline default; deterministic responses, no provider transmission.
- `LLM_MODE=live`: requires `LLM_MODEL=gpt-5.5`, endpoint, and key; Responses adapter only.
- `PRODUCT_EVIDENCE_DESTINATION=external_provider|local_service`: explicit endpoint disclosure.
  Local requires a private/loopback IP or localhost HTTP(S) endpoint. This describes the configured
  connection, not a proxy's downstream routing; it does not activate Qwen or validate a new adapter.
- Disabled, unknown, unavailable, or invalid profiles have no fallback. Incomplete global live
  settings retain the existing startup validation error. Product configuration errors return 503.

Restart the backend after configuration changes. Each run captures a private settings/registry
snapshot at creation; all B0/B1/RegBridge calls and retries use it. B2 makes no model calls.
Endpoint and adapter identity, mode, timeout, limits, reasoning configuration, and retry policy
participate in the product fingerprint; credentials are excluded and endpoint URLs are not
returned. Historical records retain original attribution. Requested model and provider-reported
model are distinct. Fixture/skipped calls do not invent provider identity. Construction failures
record zero attempts and `not-executed`, terminate the job, and issue no regulatory decision.

## Results UX refinement after d92cf03

Presentation v1.1.0 separates the action queue from a leaf-based document inventory. The queue
uses Area / What was found / Next step / Documents / Status, with distinct document placement,
manufacturer metadata, applicant information, inspection, coverage, history and service items.
The inventory shows title, filename, source section, assessment statuses and review-item count,
keyed by leaf ID. Shared filenames never collapse separate leaf contexts. Counts explicitly use
document leaves and review items; statuses and review items may overlap.

`ProductExplanation.observations` is an optional additive product field. At execution time it
retains the existing selected metadata plan and package applicant, copies exact mappings from
the rules actually represented by accepted findings, and associates keywords with those
findings. A transparent observer of the existing semantic call retains categories only for
findings accepted by the analyzer with matching IDs/citations. It changes no request, prompt,
model execution record, decision or graph. B0/B1 receive only their supplied input context;
they receive no RegBridge mapping, finding category, rule reasoning or graph.

Applicant information shows the actual cited document passage and the parsed package applicant
with explicit source labels. It does not invent a separately extracted document-applicant name.
Direct approaches may label an applicant-containing cited passage as applicant information;
that source-topic label does not assert a mismatch. Their native conclusion remains available.
Raw manufacturer values come from parsed keywords. Intent confirmation, incomplete inspection,
and partitioning uncertainty remain separate conditions. Selected preservation is acknowledged,
and neither a raw value nor an abstention independently creates an invalidity claim.

Concise queue actions link to the original overall document recommendation. Expanded details
retain complete context-group creation, suspension, identifier-reuse instructions, human
approval, findings, limitations, evidence and technical disclosures. Additional observation
items are not separately invented repairs. Older records without structured observations keep
available original detail; missing structured mapping/category information is not reconstructed
from rationale or graph labels.

The refinement does not adapt historical verifiers, normalize protected files, or change frozen
digests. Existing CRLF and M4.2.2 old-runtime-digest blockers remain as recorded above. Changes
are left uncommitted for user review.
